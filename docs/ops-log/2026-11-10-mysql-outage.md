# 장애 주입: MySQL 중단 — 30초씩 매달리던 요청을 3초 안의 503으로

- 날짜: 2026-11-10
- 환경: 로컬 docker-compose (`prod` 프로필, MySQL 8.0 / 512MB)
- 장애 주입: [`db-fault.sh`](../../load-test/db-fault.sh)가 부하 시작 60초 뒤 MySQL 컨테이너를 멈추고(`docker stop`), 180초에 다시 띄운다. 부하는 [`openai-fault.js`](../../load-test/openai-fault.js)(`FAULT=none`)와 같은 타임라인을 쓴다. AI 추천 초당 4건, 로그인과 마이페이지 초당 2건이다.
- 동기: 1단계에서 메모리 512MB로 제한한 MySQL이 대량 DELETE 중 **OOM으로 실제로 죽었다.** 운영 EC2도 소형 인스턴스에서 MySQL을 함께 돌리므로 현실적인 장애다.

## 1. 문제와 가설

요청마다 DB를 쓰는 지점은 다음과 같다.

| 요청 | DB 사용 |
|---|---|
| 로그인, 마이페이지 | 사용자 조회 (필수) |
| AI 추천, 코스 추천 | 기능 자체는 DB가 필요 없다. 하지만 **JWT 필터가 요청마다 `userRepository.findById`를 호출**한다 |

**가설:**
1. MySQL이 죽으면 DB가 필요 없는 추천까지 실패할 것이다.
2. Hikari의 연결 대기 기본값(30초) 때문에 요청이 30초씩 매달리며 스레드가 쌓일 것이다.
3. 실패는 원인을 알 수 없는 500으로 보일 것이다.

## 2. 결과

### 개선 전 (Hikari 연결 대기 30초, 별도 처리 없음)

| 구간 | 추천 실패 | 로그인 실패 | 마이페이지 실패 | Tomcat 바쁜 스레드 | Hikari 대기 |
|---|---|---|---|---|---|
| 정상 | 0% | 0% | 0% | 15 | 0 |
| MySQL 중단 | **77%** | 82% | 70% | **170** | **170** |
| 복구 후 | 0% | 0% (최대 **7.2초**) | 0% (최대 7.0초) | 172 | 172 |

- 서버 로그에서 실패 응답은 **약 30초를 기다린 뒤 500**이었다(추천 313건, 로그인 85건, 마이페이지 58건).
- 가설 1~3이 모두 맞았다. 추천도 JWT 필터의 사용자 조회 때문에 실패했다.
- MySQL이 돌아온 뒤에도 쌓인 요청을 처리하느라 로그인이 최대 7초 걸렸다.

### 개선 후 (연결 대기 3초, DB 장애 → 503)

| 구간 | 추천 실패 | 로그인 실패 | 마이페이지 실패 | Tomcat 바쁜 스레드 | Hikari 대기 |
|---|---|---|---|---|---|
| 정상 | 0% | 0% | 0% | 15 | 0 |
| MySQL 중단 | 99% | 98% | 100% | **18** | 19 |
| 복구 후 | 4% (MySQL 기동 전 몇 초) | 8% (최대 **3.0초**) | 1% | 18 | 19 |

- 실패 응답은 **약 3초 안에 `503` + `Retry-After: 30`**이 됐다(추천 491건, 로그인 125건, 마이페이지 121건).
- Tomcat 스레드가 쌓이지 않았다(170 → 18). 복구 직후 밀린 요청도 없었다.
- 복구 구간의 일부 실패는 MySQL이 다시 연결을 받기까지 걸린 몇 초 동안 생긴 것이다.

### 정직한 해석

- **가용성은 좋아지지 않았다.** 추천 실패율은 오히려 77% → 99%로 올랐다. 개선 전에는 30초 대기가 구간 경계를 넘어가면서 일부가 다음 구간으로 밀려 집계됐을 뿐이다. 어느 쪽이든 MySQL이 죽으면 추천은 쓸 수 없었다.
- 개선된 것은 **실패하는 방식**이다.
  - 30초 매달림 → 3초 안의 명확한 503
  - 스레드 고갈 위험 제거
  - 복구 후 지연 제거
  - 장애가 "버그(500)"가 아니라 "일시적 사용 불가(503)"로 구분돼 알림과 집계가 정확해짐
- **추천을 살리려면 인증이 DB에 의존하지 않아야 한다**(아래 4장).

## 3. 개선 내용

| 변경 | 이유 |
|---|---|
| `spring.datasource.hikari.connection-timeout` 30초 → **3초** | 정상일 때 커넥션 대기는 평균 0.1ms(1단계 측정)이므로 3초면 충분하다. 장애 때 요청을 오래 붙잡지 않는다 |
| DB 연결 실패 계열 예외 → **503 + `Retry-After: 30`** (`DatabaseUnavailable`) | 의존성 장애와 코드 버그를 구분한다. 클라이언트에게 다시 시도하면 될 수 있다고 알린다 |
| **JWT 필터 안에서** DB 장애를 직접 503으로 응답 | 필터에서 던진 예외는 `@RestControllerAdvice`에 닿지 않고 일반 500이 된다 |
| readiness 헬스체크에 `db` 포함, liveness에는 미포함 | readiness는 "트래픽을 받아도 되는가", liveness는 "재시작해야 하는가"를 뜻한다. DB 장애로 앱을 재시작해도 해결되지 않고 재시작만 반복하므로 liveness에서는 뺐다. 지금은 EC2 한 대에 Nginx만 있어서 이 값을 쓰는 로드밸런서가 없다. 외부 모니터링이나 향후 확장을 위한 설정이다 |
| DB 장애 로그는 스택 트레이스 없이 WARN 한 줄 | 장애 중에는 모든 요청이 여기를 지나간다. 스택 트레이스 수백 개가 로그를 덮지 않게 했다 |

**테스트:** `DatabaseUnavailableIntegrationTest`로 JWT 필터 경로와 컨트롤러 경로 모두 503 + Retry-After를 고정했다.

## 4. 남은 결정: 인증의 DB 의존 제거 (stateless JWT 인증)

- **현재:** JWT 필터가 요청마다 사용자를 DB에서 조회한다. 컨트롤러가 인증 정보에서 쓰는 값은 `principal.getId()`뿐이다.
- **대안:** 토큰의 서명과 만료만 검증하고, `userId`로 인증 객체를 만든다. 그러면 MySQL 장애 중에도 **AI 추천과 코스 추천이 계속 동작**한다. 핵심 기능이 DB 장애와 분리된다.
- **대가:** 탈퇴하거나 차단된 사용자의 access token이 만료 전까지 유효하다.
  - **완화책:** access token을 짧게 가져가고(2-4에서 15분 예정), 탈퇴 시 refresh token을 폐기한다.
  - 요청마다 하던 DB 조회 1회도 사라진다.

## 6. 배운 점

- **빨리 실패하는 것(fail fast)도 기능이다.** 같은 장애라도 30초 매달리는 실패는 자원을 쌓아 두고 복구까지 늦춘다. 3초 안의 503은 시스템을 가볍게 유지하고, 원인도 분명히 알려준다.
- **"이 기능이 DB가 필요한가"와 "이 요청이 DB를 거치는가"는 다른 질문이다.** 추천은 DB가 필요 없지만, 인증 필터 때문에 모든 요청이 DB를 거쳤다. 장애 범위(blast radius)는 기능 설계가 아니라 실제 호출 경로가 정한다.
- **개선의 효과를 지표별로 나눠서 말해야 한다.** 실패율만 보면 개선이 없어 보이고, 스레드와 응답 시간만 보면 다 해결된 것처럼 보인다. 둘 다 보여줘야 정직하다.
