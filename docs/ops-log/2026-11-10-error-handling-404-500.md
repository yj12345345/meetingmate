# 존재하지 않는 경로가 500을 반환 + 만료 토큰이 302 리다이렉트 + 미사용 API 노출

- 날짜: 2026-11-10
- 환경: 로컬 docker-compose (`prod` 프로필)
- 관련 커밋: `fix(error): ...`, `refactor: remove unused group/place/availability API`

## 1. 문제

운영에서 존재하지 않는 경로로 요청하면 404가 아니라 **500**이 돌아왔다.
점검해 보니 같은 원인으로 생긴 문제가 더 있었다.

- 클라이언트 실수(잘못된 메서드, 깨진 JSON 등)가 전부 **서버 오류(500)** 로 집계됐다. 에러율 지표가 오염된다.
- **500이 나도 서버 로그에 아무것도 남지 않았다.** 진짜 장애가 나도 원인을 볼 수 없는 상태였다.
- 만료되거나 잘못된 토큰으로 API를 부르면 **302 → `/login`** 이 돌아왔다. 브라우저의 XHR(axios)은 리다이렉트를 따라가서 HTML 로그인 페이지나 카카오 CORS 오류를 받는다. 그래서 사용자 입장에서는 "로그인돼 있는데 추천만 계속 실패하는" 상태가 됐다.

## 2. 가설

`GlobalExceptionHandler`의 `@ExceptionHandler(Exception.class)`가 너무 넓게 잡고 있다고 봤다.
Spring MVC는 경로가 없을 때 `NoResourceFoundException`, 메서드가 틀리면 `HttpRequestMethodNotSupportedException`처럼 상태 코드가 정해진 예외를 던진다.
그런데 catch-all 핸들러가 이 예외들까지 가로채서 500으로 바꾸고 있었다.

302는 Spring Security의 `oauth2Login()` 기본 진입점(AuthenticationEntryPoint)이 모든 미인증 요청을 로그인 페이지로 보내기 때문이다.

## 3. 실험 방법

[`load-test/error-matrix.sh`](../../load-test/error-matrix.sh)로 대표적인 에러 상황 10개를 보내고, 상태 코드와 Content-Type을 표로 기록했다.

## 4. 결과

| 상황 | 기대 | 수정 전 | 수정 후 |
|---|---|---|---|
| 없는 경로 (로그인 상태) | 404 | **500** | 404 |
| 없는 경로 (API 아님) | 404 | **500** | 404 |
| 잘못된 HTTP 메서드 | 405 | **500** | 405 |
| 깨진 JSON 본문 | 400 | **500** | 400 |
| 지원하지 않는 Content-Type | 415 | **500** | 415 |
| 필수 파라미터 누락 | 400 | **500** | 400 |
| 검증 실패 (짧은 비밀번호) | 400 | 400 | 400 |
| 토큰 없이 보호된 API | 401 | **302** | 401 JSON |
| 잘못되거나 만료된 토큰 | 401 | **302** | 401 JSON |
| 정상 요청 | 200 | 200 | 200 |

**10개 중 7개가 틀린 상태 코드였고, 수정 후 10개 모두 정상이다.**
카카오 OAuth 로그인 시작(`/oauth2/authorization/kakao` → 카카오로 302)은 그대로 동작한다.

## 5. 개선

1. **`GlobalExceptionHandler`가 `ResponseEntityExceptionHandler`를 상속하게 바꿨다.**
   Spring이 표준 MVC 예외마다 이미 올바른 상태 코드를 매핑해 두었으므로, 응답 본문 모양만 `ApiResponse`로 맞추는 `handleExceptionInternal`을 오버라이드했다.
   예외를 하나씩 추가하는 방식은 빠뜨리기 쉽다. 반면 이 방식은 나중에 새로 생기는 프레임워크 예외도 자동으로 올바른 코드가 된다.
2. **예상하지 못한 예외는 `log.error`로 스택 트레이스를 남긴다.**
   로그 패턴에 요청 ID(MDC)가 있어서, 사용자가 받은 `X-Request-Id`로 해당 로그를 바로 찾을 수 있다.
   클라이언트 오류(4xx)는 정상적으로 생기는 트래픽이라 DEBUG로만 남겨 로그가 시끄럽지 않게 했다.
3. **`/api/**`의 미인증 요청에는 401 JSON 진입점을 쓴다**(`defaultAuthenticationEntryPointFor`).
   OAuth 로그인 시작 경로는 영향받지 않는다. 이 401은 다음 작업인 refresh token 인터셉터가 동작하는 기준 신호가 된다.
4. **회귀 테스트:** `ErrorResponseIntegrationTest`(실제 Security 필터 체인 포함, 7개)로 상태 코드를 고정했다. 500이 날 때 로그가 남는지도 테스트로 확인한다.

## 6. 함께 정리한 것: 미사용 모임 / 장소 / 가능시간 API 삭제

- **배경:** 서비스가 "모임 일정 조율"에서 "개인 장소 추천"으로 바뀌면서, 프론트엔드는 이 API들을 더 이상 쓰지 않았다. 그런데 백엔드에는 그대로 남아 운영에 노출돼 있었다. 그중 장소 목록 조회는 **모임 멤버인지 확인하지 않아서**, 로그인한 누구나 다른 모임의 장소 후보를 볼 수 있었다(IDOR).
- **조치:**
  - 컨트롤러, 서비스, DTO, 전용 예외, 프론트의 미사용 API 모듈을 삭제했다. 해당 경로는 이제 404다.
  - 추천 API가 `place_candidate`(다른 사용자의 모임 장소 후보)를 키워드로 검색해 프롬프트와 폴백에 쓰던 경로도 제거했다. 예전 데이터가 남아 있으면 **다른 사람의 후보 이름이 내 추천에 섞일 수 있는** 경로였다. 덤으로 추천 요청마다 하던 DB 조회가 하나 줄었다.
- **남겨 둔 것:** 엔티티와 리포지토리. 회원 탈퇴 시 그 사용자의 예전 모임 데이터를 지우는 코드가 쓰고 있다. 엔티티까지 지우면 탈퇴한 사용자의 데이터가 운영 DB에 남는다.
- **다음:** 운영 DB에서 [`legacy-group-tables-check.sql`](legacy-group-tables-check.sql)(읽기 전용, 건수만 조회)로 데이터가 있는지 확인한다. 비어 있으면 엔티티와 테이블을 정리하고, 데이터가 있으면 보존 여부를 정한 뒤 정리한다.

## 7. 배운 점

- **catch-all 예외 핸들러는 "안전망"이 아니라 "정보를 지우는 장치"가 될 수 있다.** 상태 코드는 뭉개고 로그는 남기지 않았다. 그래서 404 문제 하나가 아니라 에러율 지표와 장애 추적까지 함께 망가져 있었다.
- **API 서버의 인증 실패는 리다이렉트가 아니라 상태 코드로 알려야 한다.** 브라우저 페이지용 기본값(로그인 페이지로 302)이 SPA와 맞지 않았다.
- **쓰지 않는 기능도 운영에 노출돼 있으면 관리 대상이다.** 기능이 사라져도 엔드포인트와 데이터는 남는다. 삭제할 때는 남은 데이터(탈퇴 정리, 다른 기능에서의 참조)까지 함께 따져야 한다.
