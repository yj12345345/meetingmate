# 장애 주입: OpenAI가 응답하지 않으면 서비스 전체가 멈춘다

- 날짜: 2026-11-10
- 환경: 로컬 docker-compose (`prod` 프로필, 백엔드 CPU 2 / 메모리 768MB, Tomcat 스레드 200)
- 장애 주입: OpenAI를 대신하는 WireMock mock의 응답 방식을 관리 API로 실행 중에 바꾼다 ([`openai-fault.js`](../../load-test/openai-fault.js)의 chaos 시나리오)
- 관련 커밋: OpenAI 타임아웃, 벌크헤드, 서킷 브레이커, 재시도

## 1. 문제

이 서비스의 핵심 기능(조건 입력 → AI 장소 추천 → 선택 장소 코스 추천)은 모두 OpenAI를 호출한다.
코드는 `WebClient...block()`으로 응답을 **타임아웃 없이** 기다린다.
OpenAI가 응답하지 않으면 무슨 일이 생기는지 확인한 적이 없었다.

## 2. 가설

요청 스레드가 OpenAI 응답을 무한정 기다리며 쌓이면, Tomcat 스레드 풀(200개)이 고갈될 것이다.
그러면 AI와 상관없는 로그인과 마이페이지까지 멈추고, OpenAI가 회복돼도 묶인 스레드가 풀릴 때까지 서비스가 돌아오지 않을 것이다.

## 3. 실험 방법

- **열린 부하 모델:** AI 추천 요청이 앞 요청의 완료와 상관없이 **매초 일정한 수**로 들어온다(`constant-arrival-rate`). 실제 사용자는 서로를 기다리지 않기 때문이다.
- **피해 측정:** 로그인과 마이페이지를 초당 2건씩 함께 보내, AI 장애가 다른 기능으로 번지는지 잰다.
- **고정된 타임라인:** 0~60초 정상 → **60~180초 장애** → 180~300초 회복. 매 실행이 같은 조건이다.
- **장애 종류 `hang`:** OpenAI가 요청을 받고 300초 동안 응답하지 않는다.
- **클라이언트 타임아웃:** AI 요청은 60초다. Nginx 기본 `proxy_read_timeout`과 같게 해서 브라우저가 실제로 겪는 상황에 맞췄다.
- **수집:** 단계별로 k6 클라이언트 측 수치([`fault-summary.py`](../../load-test/fault-summary.py))와 서버 측 수치([`phase-collect.py`](../../load-test/phase-collect.py))를 남겼다. 원인은 스레드 덤프(`kill -3`)로 확인했다.

## 4. 결과

### 4-1. 개선 전: 서비스 전체 중단, OpenAI가 회복돼도 3분 넘게 돌아오지 않음 (AI 요청 초당 4건)

| 구간 | 추천 실패 | 로그인 실패 | 마이페이지 실패 | Tomcat 바쁜 스레드 |
|---|---|---|---|---|
| 정상 | 0% | 0% | 0% | 14 |
| OpenAI 장애 | 100% | 34% | 21% | **200 (고갈)** |
| **장애 제거 후** | **100%** | **100%** | **100%** | **200** |

- 장애 시작 75초 만에 Tomcat 스레드 200개가 모두 찼다.
- **로그인 성공 0건 구간이 약 3분**(t+190초 ~ t+370초) 이어졌다. **OpenAI가 회복된 뒤에도 약 3분 20초** 동안 서비스가 죽어 있었다.
- 스레드 덤프를 보면 Tomcat 실행 스레드가 전부 `OpenAiClientImpl.requestJsonContent` → `Mono.block()`에서 WAITING 상태였다.
- 회복된 시점은 mock이 지연시킨 300초가 끝난 때와 일치한다. **실제로 끝내 응답하지 않는 연결이었다면, 재시작 전까지 회복되지 않는다.**

### 4-2. 타임아웃만 적용 (연결 2초, 전체 20초)

| 조건 | 장애 중 로그인 최대 | 장애 중 Tomcat 스레드 | 회복 |
|---|---|---|---|
| AI 초당 4건 | **148 ms**, 실패 0% | 80 | 즉시 |
| AI 초당 12건 | **7.41 s** (줄 서기), 실패 0% | **200 (고갈)** | 회복 구간 초반에도 200 |

- 초당 4건에서는 이것만으로 해결됐다. 추천은 20초 뒤 FALLBACK 코스로 응답했다.
- 하지만 묶이는 스레드 수는 **도착률 × 타임아웃**이다. 4 × 20 = 80은 괜찮지만, 12 × 20 = 240은 200을 넘는다. 계산대로 다시 고갈됐다. **타임아웃은 "얼마나 오래"를 제한할 뿐 "몇 개나 동시에"를 제한하지 못한다.**

### 4-3. 타임아웃 + 벌크헤드 + 서킷 브레이커 + 재시도 (AI 초당 12건)

| 구간 | 추천 실패 | 로그인 실패 / 최대 | 마이페이지 실패 / 최대 | Tomcat 바쁜 스레드 |
|---|---|---|---|---|
| 정상 | 0% | 0% / 184 ms | 0% / 49 ms | 45 |
| OpenAI 장애 | 0% (FALLBACK) | 0% / **144 ms** | 0% / 31 ms | **101 (벌크헤드 한도)** |
| 장애 제거 후 | 0% | 0% / 208 ms | 0% / 35 ms | 42 |

**서킷 브레이커 타임라인 (t = 부하 시작)**

| 시각 | 일어난 일 |
|---|---|
| t+60초 | 장애 주입 |
| t+81초 | **OPEN**. 첫 호출들이 20초 타임아웃으로 실패하자 바로 열림 |
| t+111초 ~ | 30초마다 HALF_OPEN이 돼 시험 호출 3건을 보냄. 실패하면 다시 OPEN |
| t+180초 | 장애 제거 |
| t+217초 | **CLOSED** (장애 제거 37초 뒤) |

- 장애 구간 추천 요청의 **서버 p50은 11ms**였다. 대부분 열린 서킷이 OpenAI를 부르지 않고 즉시 FALLBACK을 돌려줬다.
- 서킷이 열리기 전 21초 동안은 벌크헤드가 한도(100)를 넘는 호출 94건을 즉시 거절해, 스레드를 지켰다.

### 4-4. 재시도 검증 ([`retry-check.sh`](../../load-test/retry-check.sh), 순차 요청 20건)

| 상황 | 처음 순서 `Retry(CB(Bulkhead))` | 최종 순서 `CB(Retry(Bulkhead))` |
|---|---|---|
| 불안정: 503과 정상이 번갈아 옴 | AI 9건 / **FALLBACK 11건, 서킷 열림** | **AI 20건**, 서킷 닫힘 |
| 지속 장애: 계속 503 | (서킷 상태가 이전 실험에서 이어져 무효) | 10건은 2번씩 시도 → 서킷 OPEN → 나머지 10건은 OpenAI를 부르지 않음 |

- **처음 순서의 문제:** 서킷 브레이커가 **재시도 한 번 한 번을 실패로 집계**했다. 그래서 재시도로 결국 성공하는 상황에서도 실패율 50%에 걸려 서킷이 열렸다.
- **해결:** 서킷 브레이커를 바깥으로 옮겨, 요청의 최종 결과만 보게 했다.
- **지속 장애에서의 효과:** 요청 20건에 OpenAI 호출은 20번이었다. 서킷이 없었다면 40번이다. 유료 API라 비용도 절반이 된다.
- 순서 변경 후 4-3 실험을 다시 돌려 결과가 같음을 확인했다. hang 장애는 타임아웃이고, 타임아웃은 재시도하지 않으므로 순서의 영향을 받지 않는다.

## 5. 개선 내용

| 장치 | 설정 | 근거 |
|---|---|---|
| 연결 타임아웃 | 2초 | 연결조차 안 되면 오래 기다릴 이유가 없음 |
| 전체 호출 타임아웃 | 20초 (`openai.call-timeout`) | mock p99는 약 8초. 실제 OpenAI가 긴 JSON을 만들면 더 걸릴 수 있어 여유를 둠. **운영 로그의 durationMs를 보고 조정할 값** |
| 벌크헤드 | 동시 100, 대기 0 | Tomcat 200 중 절반을 AI가 아닌 기능 몫으로 보장. 기다리게 하면 그 자체로 스레드를 잡으므로 즉시 거절 |
| 커넥션 풀 | 16 → 100 (벌크헤드와 같게) | Reactor Netty 기본 풀이 16개(CPU 2개 기준)라, 정상 상황에서도 동시 호출이 많으면 클라이언트 안에서 숨은 대기열이 생겼음 |
| 서킷 브레이커 | 최근 20건 중 50% 실패(또는 15초 넘는 느린 호출 80%) → 30초 OPEN → 시험 3건 | 고장 난 의존성에 계속 20초씩 기다리지 않게 함 |
| 재시도 | 1회, 429/502/503/504와 연결 오류만, 지수 백오프와 지터 | **타임아웃은 재시도하지 않음.** 이미 20초와 비용을 쓴 호출을 다시 하면 둘 다 두 배가 됨 |
| 사용자 메시지 | 일반 안내 문구로 통일 | 이전에는 `Did not observe any item within 20000ms` 같은 내부 예외 메시지가 API 응답의 `warning`에 그대로 나갔음. 이제 원인은 서버 로그(WARN)에만 남김 |

- **구현 방식:** Resilience4j **core 모듈을 직접 설정**했다([`OpenAiResilienceConfig`](../../backend/src/main/java/com/meetingmate/app/service/openai/OpenAiResilienceConfig.java)). Spring Boot 4용 스타터의 호환성을 확인할 수 없었다. 대신 설정이 코드에 모두 보여서 설명하기 쉽다.
- **관측:** 서킷 상태, 호출 결과, 벌크헤드 잔여 슬롯을 Micrometer로 내보내 Grafana 패널에 추가했다.

## 7. 한계와 남은 일

- mock 지연 분포는 가정이다. **실제 OpenAI의 지연 분포를 운영에서 재지 않았다.** 운영 접근 로그(durationMs)가 쌓이면 타임아웃 20초와 느린 호출 기준 15초를 다시 정해야 한다.
- 재시도 검증은 순차 요청 20건이다. 동시 부하에서의 재시도 폭주(retry storm)는 서킷이 막아 준다는 논리로만 확인했다.
- FALLBACK 코스는 미리 정해진 기본 코스다. 사용자에게는 "AI 대신 기본 코스"라는 안내가 보인다. 품질 저하를 받아들이고 가용성을 지키는 선택이다.

## 8. 배운 점

- **외부 API의 장애는 "그 기능의 실패"로 끝나지 않는다.** 공유 자원(스레드 풀)을 통해 상관없는 기능까지 퍼지고, 원인이 사라진 뒤에도 남는다.
- **타임아웃과 벌크헤드는 서로 다른 축을 막는다.** 묶이는 스레드 수 = 도착률 × 대기 시간이다. 타임아웃은 대기 시간을, 벌크헤드는 동시 개수를 제한한다. 한쪽만으로는 도착률이 오르면 다시 뚫린다. 이 계산이 실험 수치(80개, 240개 > 200개)와 그대로 맞았다.
- **라이브러리 기본값과 권장 순서도 검증 대상이다.** Reactor Netty 커넥션 풀 16개, 그리고 Resilience4j 데코레이터 순서는 실험하기 전까지 몰랐던 동작이었다.
- **측정을 잘못 읽을 수 있다.** 회복 시간을 처음에 "10분 이상"으로 판단했다. Prometheus 조회 범위를 미래까지 잡아서 마지막 값이 이어 붙은 것이었다. 실제 수치로 정정했다(3분 20초).
